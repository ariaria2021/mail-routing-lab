# Mail Routing Lab 仕様書

## 1. プロダクトの目的

メール配送の基本である「宛先ドメインの MX レコードを DNS で取得し、優先順位に従って SMTP サーバーへ配達を試みる」流れを、短時間で手を動かして理解する教育ゲームです。実在のDNS、SMTP、メールアドレスへは接続しません。

想定する利用者は、Web 開発経験があり、メール配送インフラの入口を視覚的に学びたい人です。

## 2. MVP のルール

プレイヤーは `example.local` の管理者です。宛先は `bob@example.local` に固定し、DNS Zone にある MX レコードが配送先候補になります。他ドメインのDNSゾーンは扱いません。

1. 送信時、宛先アドレスからドメインを取り出す。
2. 対象ドメインの MX レコードを優先度の小さい順に探索する。
3. ホストが存在し、稼働中で、メールボックスに空きがあれば受信する。
4. 宛先ホストが存在しない、またはサーバーが停止中なら、ログに理由を残して次の MX を試す。
5. 受信者のメールボックス容量不足は再送可能な配送先障害ではないため、次の MX へ切り替えず失敗として扱う。
6. 成功したメールだけを bob の受信ボックスに追加する。

最小ゲームは次の3ミッションです。

1. **壊れた MX**: `mail-broken.example.local` を `mail.example.local` に修正して配送する。
2. **フェイルオーバー**: 停止した主系を飛ばし、起動した `backup.example.local` に優先度20の予備 MX として配送する。
3. **容量不足**: 容量が満杯の `mail.example.local` を増強して配送する。

各ミッションは、まず現在の設定で配送を試して失敗を観察する。失敗後に段階ヒントを表示し、指定された受信サーバーがメールを受理するとクリアとなる。3つ目をクリアするとゲームクリアです。

## 3. データと画面

ゲーム状態は `localStorage` の `mail-routing-lab-state` に JSON で保存します。含むデータは MX レコード、SMTP サーバーの稼働状態・容量・使用数、受信メール、直近の配送ログ、直近の配送ステップ、失敗観察済み状態、メール下書きです。

- **DNS Zone**: 1つ以上のMXレコードについて、優先度とホスト名を編集・追加する。
- **SMTP サーバー**: 起動・停止と容量を操作する。停止と容量切れは配送失敗の原因になる。
- **メール作成**: From / To / 件名 / 本文を入力し、配送エンジンを呼ぶ。
- **配送経路**: 送信者、DNS、DNSが返した優先度順のMX候補、受信箱を表示する。MX候補は配送経路の直列要素ではなく選択候補として分岐表示する。送信後、配送ステップを自動再生し、未試行・試行中・失敗・成功の凡例を表示する。
- **配送ログ**: DNS照会、MXごとの接続試行、SMTPの簡略会話、成功または失敗理由を表示する。
- **受信ボックス**: 成功したメールを新しい順に表示する。

## 4. 非目標と安全性

本アプリは実メールサーバーではありません。SMTP プロトコルの待受、DNS ゾーンの公開、ユーザー認証、外部メール配信は実装しません。このゲームでは SMTP が受理した時点を配送成功として扱いますが、実際にはその後のキューイングやローカル配送が発生します。実配信には TLS、迷惑メール対策、SPF/DKIM/DMARC、逆引きDNSなど追加の運用要件が必要であり、学習ゲームの範囲外です。

## 5. 検証基準

自動テストはメールアドレスのドメイン抽出、MX未設定時の失敗、MX優先度に沿った配送、容量切れの拒否、配送ステップ列を対象にします。加えて、DOM統合テストで3ミッションを初期化からゲームクリアまで操作し、経路の再生後にも受信箱が重複しないことを確認します。公開前に、リロード後も状態が残ることを手動確認します。

## 6. 次のバージョン

MXレコードの削除と、フェイルオーバーの見える化を次に導入します。その後、SPF / DKIM / DMARCを段階的な判定カードとして追加し、迷惑メール・障害・コストを含む運営モードへ拡張します。
